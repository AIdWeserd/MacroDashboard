# Архитектура MacroDashboard

Приложение остаётся монолитом на Streamlit и Python 3.12 с локальной SQLite.
Для эксплуатации добавлены отдельные каталоги, без переноса загрузчиков и поломки
существующих импортов или команд запуска.

```text
app.py                    интерфейс Streamlit
scheduler.py              однократное обновление выбранных групп
config.py                 окружение и пути
src/                      загрузчики, storage, summary, snapshot, charts
scripts/                  команды эксплуатации и проверки запуска
  update_data.py          Linux-процесс последовательного обновления
  backup.py               согласованный backup SQLite
  check_app.py            проверка выполнения Streamlit без сети
  deploy.sh               выкладка образа и откат при ошибке
tests/                    автоматические проверки без внешних API
deploy/                   шаблоны конфигурации ВМ
docs/                     архитектура и инструкция эксплуатации
.github/workflows/        проверки, сборка, публикация, SSH-деплой
.streamlit/               конфигурация сервера
Dockerfile                общий runtime для web и updater
compose.yaml              сервисы и постоянный каталог данных
compose.local.yaml        дополнение для локальной сборки
data/                     локальные данные, исключены из Git и образа
```

`test.py` — временная ручная диагностика; не запускать как автоматический тест.
`design-mockups/`, если есть в рабочем дереве, не участвует в работе Python-сервиса.

## Поток данных

`fetch_* → scheduler → storage → macro.db → build_summary → app`.
Полное обновление также сохраняет недельный snapshot. `scheduler.py` выполняется
однократно. Контейнер `updater` запускает его сразу и повторяет через заданный
интервал после завершения предыдущего запуска. Это интервал, а не время суток.
Один процесс обновления блокирует `.update.lock` в постоянном каталоге; перезапуск
контейнера завершает дочернюю группу процессов. Ручной запуск `scheduler.py`
не использует эту блокировку: перед ним нужно остановить updater.

`MACRO_DATA_DIR` задаёт единый каталог SQLite и PDF NIFD. По умолчанию это `data/`
в корне проекта. Относительный путь разрешается от текущего рабочего каталога;
в эксплуатации используется абсолютный путь. В контейнере `/app/data` связан с
`/opt/macrodashboard/data` на ВМ. UID/GID приложения — `10001:10001`.

UI тоже пишет в SQLite: обновляет календарь и может сохранять snapshot. Поэтому
у web и updater общий каталог с правом записи. Это конфигурация для одной ВМ,
одного web и одного updater, без горизонтального масштабирования SQLite.
Хранение проверяет бизнес-ключи и объединяет новую загрузку с историей в транзакции;
пропуски не затирают сохранённые значения. Перенос на PostgreSQL потребует отдельной миграции.

## Поставка

PR запускает сборку и проверки. Push в `master` дополнительно публикует уже
проверенный образ в GHCR и запускает SSH-деплой на ВМ. Образ передаётся по digest,
файлы Compose и скрипт деплоя — из того же commit. На ВМ исходники не клонируются,
сборка не выполняется. Ключи API хранятся только в `.env` ВМ.

`current` и `previous` — ссылки на каталоги релизов. Деплой сохраняет backup,
проверяет здоровье HTTP и выполнение Streamlit. При ошибке после начала замены
восстанавливает предыдущие контейнеры; SQLite автоматически не откатывается.
Небольшой перерыв и сброс Streamlit-сессий при замене контейнера ожидаемы.
Healthcheck подтверждает работу сервера, а не полноту и свежесть макроданных.

Пошаговая настройка: [DEPLOYMENT.md](DEPLOYMENT.md).

Первый запуск без Actions: [MANUAL_DEPLOYMENT.md](MANUAL_DEPLOYMENT.md). Код
передаётся архивом и собирается на ВМ через compose.local.yaml. Отдельный проект
macrodashboard-proxy из deploy/compose.caddy.yaml запускает Caddy с host networking
Linux и проксирует localhost:8501. MACRO_DOMAIN берётся из compose.env; сертификаты
хранятся в постоянных volumes. Для этого сценария наружу открываются 80/443,
а web сохраняет bind 127.0.0.1. Автоматический SSH-деплой пока не управляет Caddy.

Переход с ручного запуска на Actions: GITHUB_ACTIONS_MIGRATION.md и github-actions.html.
Перед первым автоматическим релизом current регистрируется как manual-baseline
с локальным тегом фактически работающего образа. Это даёт deploy.sh предыдущую
версию для backup и отката, даже до первого релиза из GHCR. Caddy остаётся отдельным.

PDF-экспорт использует Playwright/Chromium. Dockerfile устанавливает системные
библиотеки и браузер в `/opt/playwright`, доступный пользователю приложения.
Зависимости новых российских загрузчиков и экспортов включены в runtime lock-файл.
